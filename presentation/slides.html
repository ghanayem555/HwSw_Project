Setup02

Why nbody & raytrace

  • Zero third-party dependencies. Checked pyproject.toml for both — only pyperf. No C-extension internals to reverse-engineer, unlike pickle or pyflate.
  • Pure numerical kernels. Both are tight floating-point loops — easy to reason about, easy to get a clean before/after signal.
  • A real hardware story. Both map onto accelerator patterns from lecture: fixed-shape MAC pipelines, dot-product/rsqrt datapaths — not a forced fit.

Setup03

First real obstacle

perf is Linux-only — nothing on macOS. Moved to the course VM (QEMU/KVM guest on naranja14). Then perf record silently produced zero samples, even though the benchmark itself ran fine.

Diagnosis: perf stat (counting) worked. perf record (sampling) needs a hardware interrupt (PMI) that KVM guests often don't forward — even when raw counting does.

Fix: swap the default hardware cycles event for the software cpu-clock event.

naranja14 — root@ubuntu
$ perf record -F 999 -g -- python3 ...
Error: perf.data has no samples!

$ perf stat -e cycles,instructions sleep 1
1742951      cycles
1284818      instructions   # 0.74 IPC
# counting works, sampling doesn't -> PMI not forwarded

$ perf record -e cpu-clock -F 999 -g -- ...
[ perf record: Captured 3.7 MB perf.data ]
Method04

How perf actually works

perf record doesn't read source code. While the program runs, it interrupts the CPU 999 times a second and asks: "what function is executing right now, and what's the call stack?" — then writes every snapshot to perf.data.

If 38% of ~49,000 snapshots caught the program inside one function, that's strong statistical evidence ~38% of runtime is spent there. No magic — repeated sampling.

reading perf_report.txt

nbody05

What nbody does

Simulates gravity between the Sun and 4 outer planets — 5 bodies, real orbital data. Direct pairwise force calculation over all 10 unique pairs, leapfrog integration.

The timed hot path calls advance(dt, iterations), which runs the 10-pair update 20,000 times per benchmark call. Pure Python floats and lists — no numpy.

nbody — profiling06
nbody_flamegraph.svgperf record -e cpu-clock, 49K samples

Not the math — the bookkeeping

  • ~38% raw CPython bytecode dispatch
  • list_ass_item / list_ass_subscript — indexed writes like v1[0] -= ..., done ~75×/iteration × 20,000 = 1.5M times
  • PyFloat_FromDouble / float_dealloc — every float is a heap object, allocated and freed constantly

Conclusion: the cost is doing the math through Python's object model 1.5M times, not the math itself.

nbody — from finding to code07

How do we know it's advance()?

perf's call-graph shows raw hex addresses, not "advance()" — CPython's bytecode loop breaks stack unwinding for Python-level frames. So this is an inference, not a direct readout:

  • list_ass_item fires on container[i] = value
  • Volume check: report_energy() runs 2× per call — can't explain multi-percent cost. Only advance()'s 200,000-execution inner loop can.
advance() — the exact lines
v1[0] -= dx * b2m   # list_ass_item
v1[1] -= dy * b2m   # list_ass_item
v1[2] -= dz * b2m   # list_ass_item
v2[0] += dx * b1m   # list_ass_item
v2[1] += dy * b1m   # list_ass_item
v2[2] += dz * b1m   # list_ass_item

6 writes × 10 pairs × 20,000
= 1.2M indexed writes
(+ 3 more per body in the pos. pass)
nbody — optimization08

Three attempts, measured — not assumed

AttemptHypothesisMeasured (raw loop)Verdict
1 · sqrt() instead of **-1.5 non-integer pow() is slow in CPython 119ms → 121ms ✗ no effect
2 · numpy vectorization batch all 10 pairs per timestep 185ms → 177ms ✗ only ~4% — call overhead > N=10
3 · loop unrolling defer 1.5M indexed list writes to once 185ms → 90.5ms ✓ 51% faster

Attempt 3 works because the 5 bodies are a fixed dataset — the pair loop can be fully unrolled into plain local variables, writing back to lists once per advance() call instead of every iteration.

raytrace10

What raytrace does

A recursive Whitted-style ray tracer. 100×100 image, 8 objects (spheres + checkerboard floor), 2 lights, up to 3 reflection bounces.

Hand-rolled Vector/Point classes, no acceleration structure — every ray linearly tests all 8 objects, casts shadow rays, and recurses on reflection.

Scene objects × pixels
8 × 10,000
Baseline (Linux VM)
799ms ±8
raytrace — profiling11
raytrace_flamegraph.svg209K samples

A different bottleneck entirely

  • ~9.5% function-call/stack-frame overhead — every .dot()/.cross() is a full Python call
  • _PyDict_GetItemHint / insertdict — Vector/Point had no __slots__, so every self.x is a dict lookup
  • _PyType_Lookup — method resolution on every call

Conclusion: the cost is the OOP structure itself, not the geometry — a distinct root cause from nbody.

raytrace — from finding to code12

A genuinely different fingerprint

frame_dealloc, _PyEval_Vector, _PyDict_GetItemHint — none of these appeared in nbody's profile at all. Same symptom (slow Python), different root cause.

  • _PyDict_GetItemHint fires on self.x — only possible because Vector has no __slots__
  • frame_dealloc / _PyEval_Vector fire on every function call — .dot(), .cross(), .normalized() each pay this, thousands of times per pixel across recursion + shadow rays

raytrace — optimization13

One line per class: __slots__

Declares each class's fixed attributes up front — removes the per-instance __dict__ entirely. Zero behavior change, directly targets the profiled dict-lookup cost.

src/raytrace_optimized.py
class Vector(object):
    __slots__ = ('x', 'y', 'z')
    def __init__(self, x, y, z):
        self.x, self.y, self.z = x, y, z

−13.3% · ±7–8ms std dev

Hardware accelerator — nbody15

Run the whole loop, not one op

The profiler said the cost is per-operation overhead. Accelerating one multiply doesn't help if the CPU still dispatches through software 1.5M times.

So the accelerator runs all 20,000 iterations autonomously in hardware. The host touches it twice: write state + trigger, then read the result.

SystemVerilog · IEEE-754 float32 · hw/nbody_accelerator_fp32.sv · verified in simulation
Hardware — the conductor16

nbody_core — the control state machine

Same two-pass structure as Python's advance() — just run as a circuit, not interpreted.

hw/nbody_accelerator_fp32.sv — state sequence, per pair
S_IDLE    wait for host START
S_LOAD_I / S_LOAD_J    read body i, j from body_regfile
S_SUB     dx,dy,dz = pos_i - pos_j
S_SQ      dx², dy², dz²         (fp_mul, 0 cyc)
S_SUM     d2 = dx²+dy²+dz²
S_SQRT    √d2                    (fp_sqrt, 25 cyc)
S_DENOM   denom = d2 · √d2
S_DIV     mag = dt / denom          (fp_div, 49 cyc)
S_MASSMUL b_i = m_j·mag, b_j = m_i·mag
S_VELUPD  write vel_i, vel_j back
S_NEXTPAIR  → pair_idx++, loop (×10)
S_POSUPD  → update all 5 positions
S_NEXTITER  → iter--, loop (×20,000) or DONE

Be ready for19

Likely questions

  • "How does perf actually work?" — sampling: interrupts the CPU hundreds of times/sec, records what's executing.
  • "How did you know it was inside advance()?" — perf's Python-level call graph is broken (computed gotos); inferred from execution-count volume + matching named functions to code patterns.
  • "Why did numpy barely help?" — only 10 elements; numpy's per-call overhead cancels the benefit at that scale.
  • "Why two completely different fixes for two Python benchmarks?" — different root causes: indexed writes (nbody) vs. dict-backed attributes + call overhead (raytrace).
  • "Why accelerate the whole loop, not one operation?" — the cost is per-operation software dispatch, paid 1.5M times; one fast multiply doesn't remove that.
  • "How solid is the 125ms hardware number?" — the 1250 cycles/iteration is a real, simulated measurement (Icarus Verilog), confirmed identical at N=1,2,5,200,1000,20000; only the 200MHz clock is an assumption, since the design wasn't synthesized/timed.
  • "Did the hardware actually work the first time?" — no. Building the first full-system testbench (real data through real MMIO, not just the arithmetic units) found two real bugs: an address-range off-by-one that silently dropped uranus/neptune, and a write-enable timing bug that zeroed every other body's velocity-x. Both fixed and re-verified.
  • "Why does accuracy get so much worse at N=20,000?" — N-body systems are chaotic; any precision difference (float32 vs. Python's float64) diverges exponentially over enough steps. Energy conservation (1e-5 relative error) is the invariant that actually validates correctness at that scale, not position-by-position matching.
